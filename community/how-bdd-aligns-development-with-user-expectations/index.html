How BDD aligns development with user expectations

Work with Sean

Lesson 4 of 11 in Module 2

Agency lessons. How the Sean Dinwiddie’s Webmastery team builds custom software: user stories, behavior-driven development and functional programming. Every level starts with the Introduction, and the course outline maps every module.

October 28, 2023· Development
Sean Dinwiddie

Alignment is the point of behavior-driven development (BDD): what gets built should match what the people who use the software expect and need. Seven practices hold it in line, and the owner’s reading keeps the practices honest.

  1. User-centric perspective: Alignment needs something to align with: what users expect the software to do, written in their terms before anything is built. Every later step is checked against it.
  2. Behavior specifications: Expectations are written down as Given-When-Then scenarios, from the user’s viewpoint: a structured way to say what users expect and how the software should respond to each action.
  3. Collaboration: The owner and the people who use the result read the scenarios with the webmaster before work starts, while a scenario that misses the need is still a sentence to fix rather than code to undo.
  4. Common language: Scenarios are written in a common, accessible language: the owner’s own words for the business. The owner and the webmasters read the same words, so the scenario the owner approves is the one the test runs.
  5. Continuous feedback: Alignment is checked more than once: the owner reads each scenario before work starts, its test runs on every change after, and a scenario that no longer matches what users expect is rewritten rather than kept passing.
  6. Automated tests: Each scenario becomes an automated test that checks the software behaves as its users expect. Run on every change, the tests show that the software still does what its scenarios describe, even as it evolves. In a Redux Toolkit app, those tests run a slice through a scenario’s events; the lecture Redux Standard Patterns and Functional Programming models the events and transitions they check.
  7. Documentation: The scenarios are living documentation: a clear, readable record of how the software is expected to work: a new team member’s first read, and one shared understanding for the life of the project.

Where alignment slips

Two checks keep three things in line, and only one of them is a test:

The rule behind the examples. A scenario can pass while the need it was written for fails. In Identifying user needs, a food truck asks for its menu on the site as a PDF. “Given the menu PDF is uploaded, When a customer opens the menu page, Then the PDF opens” passes every day, and every day a customer walks over for brisket that sold out at one. The tests aligned the code with the request, not with the need.

The alignment check sits earlier, when the owner reads the stories and scenarios in the written scope and can say whether they describe what goes wrong now; the scenario that matters names what the customer would notice, a sold-out item shown as sold out. BDD keeps the code honest to its scenarios, and the owner’s reading keeps the scenarios honest to the need.

With these practices, and the owner reading the scenarios against the need, BDD keeps development aligned with what users expect. The owner and the team share one record of what the software should do, and a test says the moment it stops doing it.
