The same order, typed twice

An order comes in by phone or email. Someone types it into the register, then again into the calendar and the order sheet.

None of it is hard, and all of it has to happen, every day.

Lesson: Automating a business process with a person in the loop · The first job on Automation

Ask the room who types the same details into two systems, and let the hands go up. This is the first job on the automation page, and the job the whole module builds.

What the retyping costs

  • A typo between two screens, and the customer finds it first.
  • The admin, done at night after closing.
  • One person is the system, and when they’re away it stops.

Everyone here can put their own number on it.

No figures from the front of the room. Ask what happens when the calendar and the register disagree, and who does the typing on a day off. Let the owners name their own cost.

SI: what federal agencies now call AI

Since September 29, 2026, federal agencies write Super Intelligence, SI, in their own documents and communications, where they wrote artificial intelligence, AI.

Executive Order 14434 changes the name, not the law: it defines SI by the statutory definition of AI, so the two cover the same systems. Proposed language for a federal definition is due to the President within 60 days.

In research, “superintelligence” means something else. Here, SI is only the new name.

Sources: the order and its fact sheet · The course’s modules keep “AI” in their names: Module 5

Say it once, plainly, and move on. The order is titled “Inaugurating the Era of Super Intelligence.” It binds the executive branch’s departments and agencies from now on, and leaves statutes, regulations and earlier documents as they are. For its purposes SI means what the statutory definition of AI, 15 U.S.C. 9401(3), covers, and the legal summaries agree it changes no law. No claim about what the systems can do rides on the name, and from here on the talk says SI.

An agent is a loop

An agent is software: a model in a loop with tools.

It reads the job, asks for a tool, reads the result and goes round again, until it answers or a limit stops it.

Every way out is a value the program names.

Lesson: The agent loop and its tools

The whole trick, and it is ordinary software. The four ways out are answered, out of turns, out of tokens and stopped by the model. The lesson builds the loop in TypeScript and tests it against a scripted model, so no test calls a real one.

The model asks; the program decides

The model never runs anything. It asks for a tool by name, and plain code checks the request and decides whether to run it.

Ask an invented bakery for croissants it doesn’t bake, and the tool answers with what the menu does have, so the model offers something real.

Lesson: The agent loop and its tools

Every rule in the module lives on the program’s side of that line. A failed tool is a result the model reads on its next turn, never a crash, so it can say plainly that there are no croissants instead of inventing one.

A skill is packaged know-how

A skill is a folder with a SKILL.md: a name, a description and instructions, with scripts beside them.

Only the name and description load at the start. The instructions load when a task matches, and a script runs only when a step calls it.

Lesson: Writing an agentic skill

Staged loading is why a team can install many skills at little cost, and why the description carries the weight: it is the only part the model reads before deciding. A script’s output enters the context, never its code. Anthropic published the format as an open standard in December 2025.

Judgment to the model, exact work to code

Which times are open is arithmetic, so a script works them out and a second script checks the draft. How to word the reply is judgment, and the instructions leave room for it.

$ node scripts/check-draft.ts draft.txt open-times.json
offers 10:30 a.m., which open-times.json doesn't list
offers 4 times; the stock reply offers at most 3
still holds the placeholder {first name}

The model fixes all three, and the check runs again.

Lesson: Writing an agentic skill

A model writing times token by token can offer one that isn’t free; a script can’t. Instructions for flexible guidance, code for reliability. A check holds only where code runs it on every draft, whatever the model did.

A person approves what leaves the building

Inside, the agent reads and drafts. At the door stands a person.

An email sent, a payment taken, a record deleted or a slot booked waits for a yes.

A draft costs nothing to throw away. A sent email can’t be unsent.

Lesson: Automating a business process with a person in the loop

The gate is plain data and pure functions. It takes the task and the tool’s name and nothing else, so no email can change its answer. OWASP calls the failure this guards against excessive agency.

Each task gets only its tools

The order-entry agent reads the email, looks up the menu and drafts. It has no tool that sends email at all.

Its tools can’t reach the register, the calendar or the order sheet; only an approval can. More reach is a decision, made on purpose, with a test that names it.

Lesson: Automating a business process with a person in the loop

Least privilege, at the scale of a bakery. Add a tool to the agent’s list and a scenario fails, naming the new tool, so widening its reach is always someone’s deliberate change.

An email’s words are data, never orders

An email can say anything: that the owner approved it, to enter it now, to send the week’s orders to a stranger. The program holds the line, not the model. Each call’s verdict, from the log:

ran         read_order
held        draft_order
refused     enter_sale
refused     send_email

OWASP’s 2026 list ranks prompt injection first among the risks to apps built on large language models.

Lesson: Automating a business process with a person in the loop

The model in the lesson is scripted to obey the email, the worst case. Both requests are refused and logged for the owner to see, and the draft that waits is the order the customer asked for, priced from the menu. No defense makes a model immune; this design limits what a fooled one can do.

Tests every run, evals on real days

  • Tests run the loop against a scripted model: quick, and the same on every run.
  • Evals run the real model over real days’ email, before and after every change.

Each email, with what the person did with it, becomes an eval case, so the evals follow the real mix of orders and questions.

Lesson: Automating a business process with a person in the loop

A scripted model tests the plumbing; it can’t say whether a real model drafts the right order. The evals are where the automation page’s promise, tested against real days rather than a demo, is kept.

Handover, with written notes

At handover the agent runs in the owner’s own accounts, and each order is checked once instead of typed into three systems, so the retyping after closing goes with it. The notes say:

  • what it does on its own, and what waits for you;
  • what it can’t do at all, and how to read its log;
  • what happens when it stops: orders typed by hand, as before, with nothing lost.

Keeping it watched and current is part of the monthly engagement.

Written down, so a new hire can pick it up. The last line is the automation page’s own: after handover, changes go on the month’s written work list.

Fair questions from owners

Is this hype?

It’s software you can test: a loop, typed tools, a scenario for every rule and a log you can read.

Things change too fast.

Models change. The written scope, the tests and the evals stay, and every change runs against real days before it reaches the counter.

And not every job needs an agent: when the steps never change, a script, or a setting you already pay for, does it for less.

Answer calmly. The last line is the honest part, and the module’s own advice: the simplest thing that works, and an agent only where the input varies and a wrong step is caught before it leaves the building.
